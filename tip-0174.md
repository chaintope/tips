# Introduction
## Abstract

This document describes a binary format for a Partially Signed Tapyrus Transaction (PSTT), which contains the data of a not-yet-signed Tapyrus transaction together with the metadata that signers need in order to produce signatures for it. A PSTT can be passed between multiple parties — each adding inputs, outputs, data, or signatures — and finally be converted into a fully signed, network-valid Tapyrus transaction.

The format is modeled on Bitcoin's PSBT. Its data model follows BIP-370 (PSBT version 2)[^5]: the transaction is represented as per-input and per-output fields rather than as a single fixed unsigned transaction, so that inputs and outputs can be added after creation and after some signatures have been collected. This makes the format support, within the format itself, the fee provider pattern — a service supplying the TPC input that pays the fee of a Colored Coin transaction on behalf of a user. The container encoding and the signing-related fields follow BIP-174[^1].

Fields that exist in BIP-174 and BIP-370 only to support Segregated Witness are not part of this format, because Tapyrus does not implement Segregated Witness. Instead, this format accounts for the Tapyrus-specific features: the immutable transaction identifier (malleability-fixed txid)[^2], Colored Coins (`OP_COLOR`)[^3], and Schnorr signatures in script[^4].

## Motivation

Creating a fully signed Tapyrus transaction often involves more than one party: multisig wallets, hardware wallets and other offline signers, token issuers, and services that co-sign on behalf of users. These parties need a standard way to exchange a transaction that is not yet fully signed, along with the information required to sign it — the UTXOs being spent, redeem scripts, and BIP 32 derivation paths.

Passing around a raw transaction in network serialization is insufficient. A raw transaction cannot carry per-input metadata, cannot hold more than one signature per input before the scriptSig is assembled, and gives a signer no way to verify the amount or the color of the coins it is spending. Bitcoin solved this problem with BIP-174; however, a Bitcoin PSBT cannot represent a Tapyrus transaction because Tapyrus transactions differ in serialization (`features` field), reference previous transactions by the malleability-fixed txid, and may carry Colored Coin outputs whose token semantics a signer must be able to inspect.

A format in which the unsigned transaction is fixed at creation also cannot express workflows in which the set of inputs and outputs is negotiated between parties. The most important such workflow in Tapyrus is fee provision: every Tapyrus transaction must pay its fee in TPC, so a user who holds only Colored Coins cannot construct a complete transaction alone — a fee provider must add a TPC input (and possibly a change output) to the user's transaction. For this reason, this format adopts the constructable data model of BIP-370 as its only representation, rather than the fixed-transaction model of BIP-174.

# Specification

The Partially Signed Tapyrus Transaction (PSTT) format consists of key-value maps. Each map consists of a sequence of key-value records, terminated by a `0x00` byte.

```
<pstt> := <magic> <global-map> <input-map>* <output-map>*
<magic> := 0x70 0x73 0x74 0x74 0xFF
<global-map> := <keypair>* 0x00
<input-map> := <keypair>* 0x00
<output-map> := <keypair>* 0x00
<keypair> := <key> <value>
<key> := <keylen> <keytype> <keydata>
<value> := <valuelen> <valuedata>
```

Where:

* `<magic>` is the ASCII string `pstt` followed by the separator byte `0xFF`. The magic distinguishes a PSTT from a raw Tapyrus transaction and from a Bitcoin PSBT (whose magic is `psbt 0xFF`).
* `<keylen>` is a compact size unsigned integer containing the combined length of `<keytype>` and `<keydata>`.
* `<keytype>` is a compact size unsigned integer representing the type of the record. It must be minimally encoded.
* `<keydata>` is the type-dependent key data.
* `<valuelen>` is a compact size unsigned integer containing the length of `<valuedata>`.
* `<valuedata>` is the type-dependent value data.

Compact size unsigned integers use the same encoding as Tapyrus network serialization (Bitcoin-style `CompactSize`).

There must not be two records within a single map with the same complete key (`<keytype>` and `<keydata>`).

The first map is the global map. It is followed by one input map per input of the transaction, in the same order as the inputs, and then one output map per output of the transaction, in the same order as the outputs. The numbers of input and output maps must match `PSTT_GLOBAL_INPUT_COUNT` and `PSTT_GLOBAL_OUTPUT_COUNT`. A PSTT violating this is invalid.

For binary transport and storage, the raw binary format is used. For display and text transport, Base64 encoding of the raw binary format is used.

## Version

The version of a PSTT is given by the `PSTT_GLOBAL_VERSION` field; if the field is absent, the version is 0. This TIP defines **version 0**, the only version of the format. Software encountering a PSTT with a higher version number must reject it.

**Note (informative):** PSTT version numbers do not correspond to Bitcoin PSBT version numbers. PSTT version 0 uses the data model of *PSBT version 2* (BIP-370); no PSTT version uses the fixed-transaction model of BIP-174 (PSBT version 0). An earlier draft of this TIP defined both models as PSTT version 0 and PSTT version 2, mirroring Bitcoin. This was abandoned: Bitcoin keeps both versions only because of its installed base of PSBT-version-0 implementations, which Tapyrus does not have, and the BIP-370 model can express every workflow the BIP-174 model can (create the transaction fully, then immediately clear the modifiable flags). Defining a single version halves the specification and implementation surface — no per-version branching in any role, no exclusion rules between the global unsigned transaction and the per-input/per-output fields, and no cross-version conversion. Individual field type values still follow BIP-174/BIP-370 (see [Backwards Compatibility](#backwards-compatibility)), so this numbering difference affects only the `PSTT_GLOBAL_VERSION` value, not field semantics.

## Transaction Serialization

Several fields carry or produce a complete Tapyrus transaction, serialized in the Tapyrus network format:

```
<tx> := <features> <num inputs> <input>* <num outputs> <output>* <locktime>
```

* `<features>`: 32-bit little endian signed integer (currently `1`).
* `<input>`: outpoint (`<txid> <index>`), scriptSig, and sequence number. The `<txid>` of the outpoint is the malleability-fixed txid (`hashMalFix`) of the previous transaction.
* `<output>`: 64-bit little endian signed integer amount, followed by the scriptPubKey.
* `<locktime>`: 32-bit little endian unsigned integer.

## Global Types

| Name | `<keytype>` | `<keydata>` | `<valuedata>` | Description |
|---|---|---|---|---|
| Extended Public Key | `PSTT_GLOBAL_XPUB = 0x01` | `<xpub>` The 78-byte serialized extended public key as defined by BIP 32. | `<fingerprint> <32-bit uint>*` The master key fingerprint as defined by BIP 32 concatenated with the derivation path of the public key, as a sequence of 32-bit little endian unsigned integers. | An extended public key from which keys used in the transaction can be derived. |
| Transaction Features | `PSTT_GLOBAL_TX_FEATURES = 0x02` | None | `<32-bit int>` Little endian. | The `features` field of the transaction. The only value currently defined by Tapyrus is `1`. **Required.** |
| Fallback Locktime | `PSTT_GLOBAL_FALLBACK_LOCKTIME = 0x03` | None | `<32-bit uint>` Little endian. | The locktime to use if no input specifies a required locktime. If omitted, it is assumed to be 0. |
| Input Count | `PSTT_GLOBAL_INPUT_COUNT = 0x04` | None | `<compact size uint>` | The number of inputs in this PSTT. **Required.** |
| Output Count | `PSTT_GLOBAL_OUTPUT_COUNT = 0x05` | None | `<compact size uint>` | The number of outputs in this PSTT. **Required.** |
| Transaction Modifiable Flags | `PSTT_GLOBAL_TX_MODIFIABLE = 0x06` | None | `<8-bit uint>` Bitfield. | Whether the transaction can still be modified. See [Transaction Modifiable Flags](#transaction-modifiable-flags). |
| PSTT Version | `PSTT_GLOBAL_VERSION = 0xFB` | None | `<32-bit uint>` Little endian. | The version number of this PSTT. If omitted, the version number is 0. |
| Proprietary | `PSTT_GLOBAL_PROPRIETARY = 0xFC` | `<identifierlen> <identifier> <subtype> <subkeydata>` | Any value data as defined by the proprietary type user. | For use by applications that need non-standardized fields. |

Type value `0x00` is reserved and must not be used. It is the global unsigned transaction of BIP-174, which has no counterpart in this format (see the note in [Version](#version)).

### Transaction Modifiable Flags

The value of `PSTT_GLOBAL_TX_MODIFIABLE` is a single-byte bitfield:

* **Bit 0 — Inputs Modifiable**: if set, inputs may still be added or removed.
* **Bit 1 — Outputs Modifiable**: if set, outputs may still be added or removed.
* **Bit 2 — Has SIGHASH_SINGLE**: if set, the PSTT contains at least one signature made with `SIGHASH_SINGLE`, so the correspondence between input and output positions must be preserved by any modification.
* The remaining bits are reserved and must be set to 0.

If the field is omitted, the transaction is not modifiable.

## Input Types

| Name | `<keytype>` | `<keydata>` | `<valuedata>` | Description |
|---|---|---|---|---|
| Previous Transaction | `PSTT_IN_UTXO = 0x00` | None | `<tx>` | The complete previous transaction, in Tapyrus network serialization, that contains the output being spent by this input. |
| Partial Signature | `PSTT_IN_PARTIAL_SIG = 0x02` | `<pubkey>` The public key (33-byte compressed or 65-byte uncompressed) corresponding to this signature. | `<signature>` | A signature for this input. See [Signatures](#signatures). |
| Sighash Type | `PSTT_IN_SIGHASH_TYPE = 0x03` | None | `<32-bit uint>` Little endian. | The sighash type to be used for this input. Signatures for this input must use this sighash type. |
| Redeem Script | `PSTT_IN_REDEEM_SCRIPT = 0x04` | None | `<script>` | The redeem script for this input, if the output being spent is P2SH or CP2SH. |
| BIP 32 Derivation Path | `PSTT_IN_BIP32_DERIVATION = 0x06` | `<pubkey>` The public key. | `<fingerprint> <32-bit uint>*` The master key fingerprint concatenated with the derivation path, as a sequence of 32-bit little endian unsigned integers. | The derivation path of the public key needed to sign this input. |
| Finalized scriptSig | `PSTT_IN_FINAL_SCRIPTSIG = 0x07` | None | `<script>` | The complete, final scriptSig for this input. |
| RIPEMD160 Preimage | `PSTT_IN_RIPEMD160 = 0x0a` | `<20-byte hash>` | `<preimage>` | The preimage for a RIPEMD160 hash needed to spend this input. |
| SHA256 Preimage | `PSTT_IN_SHA256 = 0x0b` | `<32-byte hash>` | `<preimage>` | The preimage for a SHA256 hash needed to spend this input. |
| HASH160 Preimage | `PSTT_IN_HASH160 = 0x0c` | `<20-byte hash>` | `<preimage>` | The preimage for a HASH160 hash needed to spend this input. |
| HASH256 Preimage | `PSTT_IN_HASH256 = 0x0d` | `<32-byte hash>` | `<preimage>` | The preimage for a HASH256 hash needed to spend this input. |
| Previous TXID | `PSTT_IN_PREVIOUS_TXID = 0x0e` | None | `<32-byte txid>` | The malleability-fixed txid (`hashMalFix`) of the transaction containing the output being spent. **Required.** |
| Spent Output Index | `PSTT_IN_OUTPUT_INDEX = 0x0f` | None | `<32-bit uint>` Little endian. | The index of the output being spent in the transaction identified by `PSTT_IN_PREVIOUS_TXID`. **Required.** |
| Sequence Number | `PSTT_IN_SEQUENCE = 0x10` | None | `<32-bit uint>` Little endian. | The sequence number of this input. If omitted, the sequence number is `0xFFFFFFFF`. |
| Required Time-based Locktime | `PSTT_IN_REQUIRED_TIME_LOCKTIME = 0x11` | None | `<32-bit uint>` Little endian. Must be greater than or equal to 500000000. | The minimum Unix timestamp that the transaction's locktime must be, for this input to be spendable. |
| Required Height-based Locktime | `PSTT_IN_REQUIRED_HEIGHT_LOCKTIME = 0x12` | None | `<32-bit uint>` Little endian. Must be greater than 0 and less than 500000000. | The minimum block height that the transaction's locktime must be, for this input to be spendable. |
| Proprietary | `PSTT_IN_PROPRIETARY = 0xFC` | `<identifierlen> <identifier> <subtype> <subkeydata>` | Any value data as defined by the proprietary type user. | For use by applications that need non-standardized fields. |

Type values `0x01` (witness UTXO), `0x05` (witness script), `0x08` (finalized scriptWitness), and `0x09` (proof-of-reserves commitment), as well as the Taproot-related type values defined by Bitcoin BIPs, are reserved and must not be used. They correspond to Segregated Witness and Taproot fields in BIP-174 and its successors, which have no meaning in Tapyrus.

Unlike BIP-174, which distinguishes between a full previous transaction (for non-witness inputs) and a standalone `TxOut` (for witness inputs), this format defines only the full previous transaction. The Tapyrus signature hash algorithm does not commit to the amount or the scriptPubKey of the output being spent, so a signer can only trust these values — including the color identifier of a Colored Coin output — by receiving the complete previous transaction and verifying its txid. `PSTT_IN_UTXO` must therefore be attached to every input before that input can be signed, in addition to the required `PSTT_IN_PREVIOUS_TXID` and `PSTT_IN_OUTPUT_INDEX` fields. See [Rationale](#rationale).

| Name | `<keytype>` | `<keydata>` | `<valuedata>` | Description |
|---|---|---|---|---|
| Redeem Script | `PSTT_OUT_REDEEM_SCRIPT = 0x00` | None | `<script>` | The redeem script for this output, if the output is P2SH or CP2SH. |
| BIP 32 Derivation Path | `PSTT_OUT_BIP32_DERIVATION = 0x02` | `<pubkey>` The public key. | `<fingerprint> <32-bit uint>*` The master key fingerprint concatenated with the derivation path, as a sequence of 32-bit little endian unsigned integers. | The derivation path of the public key involved in this output. Allows a signer to verify change outputs. |
| Output Amount | `PSTT_OUT_AMOUNT = 0x03` | None | `<64-bit int>` Little endian. | The amount of this output. For a colored output, the amount denominates tokens of the output's color; otherwise it denominates tapy (TPC). **Required.** |
| Output Script | `PSTT_OUT_SCRIPT = 0x04` | None | `<script>` | The scriptPubKey of this output. For a colored output this includes the `<color identifier> OP_COLOR` prefix. **Required.** |
| Proprietary | `PSTT_OUT_PROPRIETARY = 0xFC` | `<identifierlen> <identifier> <subtype> <subkeydata>` | Any value data as defined by the proprietary type user. | For use by applications that need non-standardized fields. |

Type value `0x01` (witness script) and the Taproot-related type values are reserved and must not be used, for the same reason as in the input map.

## Signatures

The value of a `PSTT_IN_PARTIAL_SIG` record is a signature in one of the two schemes supported by Tapyrus script:

* **ECDSA**: a DER-encoded ECDSA signature followed by the 1-byte sighash type. The total length is variable (typically 71–73 bytes).
* **Schnorr**: a 64-byte Schnorr signature (32-byte `r` followed by 32-byte `s`) followed by the 1-byte sighash type, for a total of exactly 65 bytes.

This matches the rule of the Tapyrus script interpreter, in which a 65-byte signature is verified as a Schnorr signature and any other length as an ECDSA signature[^4]. In a multisig script, all signatures must use the same scheme; Tapyrus does not allow mixing ECDSA and Schnorr signatures within a single `OP_CHECKMULTISIG` evaluation.

The signature hash is computed with the legacy Bitcoin signature hash algorithm over the Tapyrus serialization of the transaction determined by the PSTT's fields, with the locktime computed as described in [Determining the Locktime](#determining-the-locktime). The defined sighash types are `SIGHASH_ALL (0x01)`, `SIGHASH_NONE (0x02)`, and `SIGHASH_SINGLE (0x03)`, each optionally combined with `SIGHASH_ANYONECANPAY (0x80)`.

The scriptCode used in the signature hash computation is determined by the output being spent:

* For a P2SH or CP2SH output, the scriptCode is the redeem script. For CP2SH, the redeem script does not include the color identifier prefix (see [Colored Coins](#colored-coins)).
* For any other output, the scriptCode is the complete scriptPubKey of the output being spent. For CP2PKH, this includes the `<color identifier> OP_COLOR` prefix.

The legacy algorithm inherits Bitcoin's `SIGHASH_SINGLE` defect: for an input whose index has no corresponding output, the computed digest degenerates to a constant that does not commit to the transaction. An input whose index is greater than or equal to the number of outputs must not be signed with `SIGHASH_SINGLE`.

## Determining the Locktime

The locktime of the transaction is computed from the `PSTT_GLOBAL_FALLBACK_LOCKTIME` field and the `PSTT_IN_REQUIRED_TIME_LOCKTIME` and `PSTT_IN_REQUIRED_HEIGHT_LOCKTIME` fields of the inputs:

* If no input has a required locktime field, the locktime is the value of `PSTT_GLOBAL_FALLBACK_LOCKTIME`, or 0 if that field is omitted.
* Otherwise, one locktime kind (height-based or time-based) must be chosen that every input which specifies a required locktime can accept. An input specifying only one kind can accept only that kind; an input specifying both kinds, or neither, can accept either. If no single kind is acceptable to all such inputs, the PSTT cannot produce a valid transaction.
* If both kinds are acceptable, the height-based locktime is chosen.
* The locktime is the maximum value among the chosen kind's fields across all inputs.

## Unique Identification

A PSTT is identified by the txid of the transaction constructed from its fields, with the sequence number of every input set to 0 and the locktime computed as described above. Sequence numbers are set to 0 for identification because they may be changed after creation.

In Tapyrus the txid is the malleability-fixed hash (`hashMalFix`), which is computed without scriptSigs; the identifier is therefore unaffected by signing and finalization. It changes when inputs or outputs are added or removed, or when the computed locktime changes, so identification is meaningful once construction is complete (both modifiable flags cleared). The identifier equals the txid of the final transaction only if the final sequence number of every input is 0, because the identifier is computed with all sequence numbers set to 0.

## Colored Coins

A PSTT can represent transactions that issue, transfer, or burn Colored Coins[^3]. No dedicated field is required: the color identifier is part of the scriptPubKey of the relevant outputs.

* An input spends a colored output when the scriptPubKey of the referenced previous output follows the CP2PKH or CP2SH template, i.e. begins with `<color identifier (33 bytes)> OP_COLOR`. The amount of that output denominates tokens of that color, not TPC.
* For a CP2SH input, `PSTT_IN_REDEEM_SCRIPT` holds the script whose HASH160 appears in the scriptPubKey. The color identifier prefix (`<color identifier> OP_COLOR`) belongs to the scriptPubKey and is not part of the redeem script.
* Because the color identifier and token amount of an input are known only from the previous output, an Updater must attach `PSTT_IN_UTXO` to every input that is to be signed. This allows a Signer to compute, for each color, the token balance between inputs and outputs, and to compute the TPC fee from the uncolored inputs and outputs.
* A Signer should display to the user, or otherwise verify, the color identifier and the token amounts being spent and created, in addition to the TPC amounts.

# Roles

This section describes the responsibilities of the participants in a PSTT workflow. A single piece of software may act in several roles.

## Creator

The Creator creates a new PSTT. It sets `PSTT_GLOBAL_TX_FEATURES` (currently `1`), and initializes `PSTT_GLOBAL_INPUT_COUNT` and `PSTT_GLOBAL_OUTPUT_COUNT` to the number of inputs and outputs it creates (possibly 0). If parties other than the Creator will add inputs or outputs, the Creator must set the corresponding flags in `PSTT_GLOBAL_TX_MODIFIABLE`; otherwise it may omit the field or clear the flags to fix the transaction at creation, which reproduces the fixed-transaction workflow of BIP-174.

## Constructor

The Constructor adds inputs and outputs to the PSTT.

Before adding an input or output, the Constructor must verify that the corresponding flag of `PSTT_GLOBAL_TX_MODIFIABLE` is set. When it adds an input, it must add an input map with `PSTT_IN_PREVIOUS_TXID` and `PSTT_IN_OUTPUT_INDEX`, and increment `PSTT_GLOBAL_INPUT_COUNT`; when it adds an output, it must add an output map with `PSTT_OUT_AMOUNT` and `PSTT_OUT_SCRIPT`, and increment `PSTT_GLOBAL_OUTPUT_COUNT`.

If an added input has a required locktime field that changes the locktime computed for the transaction, and the PSTT already contains signatures, the Constructor must not add that input.

If the Has SIGHASH_SINGLE flag is set, the Constructor must preserve the positional correspondence between existing inputs and outputs: inputs and outputs may only be added in pairs at matching positions after the existing ones.

A Constructor can declare construction finished by clearing the Inputs Modifiable and Outputs Modifiable flags.

## Updater

The Updater adds information to a PSTT that later signers will need:

* For each input, the complete previous transaction in `PSTT_IN_UTXO`.
* For each P2SH or CP2SH input whose redeem script it knows, `PSTT_IN_REDEEM_SCRIPT`.
* For each public key it knows to be involved in an input or output, the `*_BIP32_DERIVATION` records.
* Optionally, `PSTT_IN_SIGHASH_TYPE` to request a specific sighash type from signers, and `PSTT_IN_SEQUENCE` to set an input's sequence number.
* Any hash preimages required to spend an input.

An Updater must not add, remove, or alter inputs and outputs; that is the Constructor's role. An Updater also must not change the sequence number of an input for which a partial signature already exists, because every signature commits to the sequence number of the input it covers.

## Signer

The Signer produces signatures. Before signing an input, the Signer:

* Must not sign an input that has no `PSTT_IN_UTXO` record: without it, the scriptCode cannot be constructed and the amount and color of the coins being spent cannot be verified. Must verify that the txid (`hashMalFix`) of the transaction in `PSTT_IN_UTXO` equals the input's `PSTT_IN_PREVIOUS_TXID`; if they do not match, the Signer must not sign the input.
* Must verify that the redeem script in `PSTT_IN_REDEEM_SCRIPT`, if present, hashes to the value committed in the scriptPubKey of the output being spent. For a CP2SH output, the hash to compare against is the one following `OP_HASH160` after the `<color identifier> OP_COLOR` prefix.
* Must use the sighash type in `PSTT_IN_SIGHASH_TYPE` if present; if the Signer cannot accept that sighash type, it must not sign. If no sighash type is specified, `SIGHASH_ALL` is recommended.
* Must compute the locktime as described in [Determining the Locktime](#determining-the-locktime) and must not sign if no valid locktime exists.
* Must not sign with `SIGHASH_SINGLE` an input whose index is greater than or equal to the number of outputs (see [Signatures](#signatures)).
* Should present to the user the TPC amounts and, for colored inputs and outputs, the color identifiers and token amounts, before signing.

For each produced signature, the Signer adds a `PSTT_IN_PARTIAL_SIG` record keyed by the corresponding public key. A Signer that uses the Schnorr scheme produces a 65-byte signature value as described in [Signatures](#signatures).

A Signer must not add a signature to a multisig input whose scheme conflicts with the scheme of signatures already present for that input.

After signing, the Signer must update `PSTT_GLOBAL_TX_MODIFIABLE`:

* If the signature does not use `SIGHASH_ANYONECANPAY`, the Inputs Modifiable flag must be cleared.
* If the base sighash type (the value with the `SIGHASH_ANYONECANPAY` bit cleared) is not `SIGHASH_NONE`, the Outputs Modifiable flag must be cleared.
* If the base sighash type is `SIGHASH_SINGLE`, the Has SIGHASH_SINGLE flag must be set.

## Combiner

The Combiner merges two or more PSTTs that have the same identifier (see [Unique Identification](#unique-identification)) into one PSTT that contains all the records of the originals. Duplicate complete keys with identical values are deduplicated. If two PSTTs contain the same complete key with different values, the Combiner may select either value, or may refuse to combine. PSTTs with different identifiers must not be combined. Unknown key types and their values must be preserved.

## Input Finalizer

The Input Finalizer checks, for each input, whether the collected records are sufficient to satisfy the script of the output being spent. If so, it constructs the complete scriptSig — for example, `<sig> <pubkey>` for P2PKH and CP2PKH, or `OP_0 <sig>* <redeem script>` for multisig inside P2SH and CP2SH — and places it in `PSTT_IN_FINAL_SCRIPTSIG`. It then removes the `PSTT_IN_PARTIAL_SIG`, `PSTT_IN_SIGHASH_TYPE`, `PSTT_IN_REDEEM_SCRIPT`, `PSTT_IN_BIP32_DERIVATION`, and preimage records for that input. All other records are retained: in particular `PSTT_IN_PREVIOUS_TXID`, `PSTT_IN_OUTPUT_INDEX`, `PSTT_IN_SEQUENCE`, and the required locktime fields must be kept because the Transaction Extractor needs them, and `PSTT_IN_UTXO` and unknown records must be kept as well.

A PSTT must not be finalized while the Inputs Modifiable or Outputs Modifiable flag is still set.

## Transaction Extractor

The Transaction Extractor verifies that every input has a `PSTT_IN_FINAL_SCRIPTSIG` record and constructs the final transaction in Tapyrus network serialization from the fields: `features` from `PSTT_GLOBAL_TX_FEATURES`; for each input, the outpoint from `PSTT_IN_PREVIOUS_TXID` and `PSTT_IN_OUTPUT_INDEX`, the scriptSig from `PSTT_IN_FINAL_SCRIPTSIG`, and the sequence number from `PSTT_IN_SEQUENCE` (or `0xFFFFFFFF` if omitted); for each output, the amount from `PSTT_OUT_AMOUNT` and the scriptPubKey from `PSTT_OUT_SCRIPT`; and the locktime as described in [Determining the Locktime](#determining-the-locktime).

The txid (`hashMalFix`) of the extracted transaction does not depend on the scriptSigs, so it is known before finalization.

# Fee Provider Workflow

This section is informative. It illustrates how a PSTT supports a **fee provider** — a service that supplies the TPC required to pay the transaction fee on behalf of a user who holds only Colored Coins. Every Tapyrus transaction must pay its fee in uncolored TPC, and token amounts do not count toward the fee, so a user without TPC cannot complete a token transfer alone.

## Non-interactive variant (exact-fee UTXO)

The fee provider maintains a pool of TPC UTXOs whose value equals the fee it pays per transaction, so that no change output is needed. The user obtains the fee amount out-of-band (e.g. from the provider's published policy) and only one message to the provider is required.

1. The user, acting as Creator and Constructor, creates a PSTT containing their token inputs (CP2PKH/CP2SH) and all token outputs. The Inputs Modifiable flag is set; no further outputs will be added.
2. The user, acting as Updater and Signer, attaches `PSTT_IN_UTXO` to their inputs and signs them with `SIGHASH_ALL | SIGHASH_ANYONECANPAY`. Each signature commits to the input it covers and to all outputs, while leaving the Inputs Modifiable flag set (the Outputs Modifiable flag is cleared by these signatures, if it was set).
3. The user sends the PSTT to the fee provider.
4. The fee provider verifies the transaction: it checks the token balances per color using the attached `PSTT_IN_UTXO` records, and checks that the transaction pays no TPC to outputs it does not expect. Acting as Constructor, it adds one TPC input of exactly the fee amount; acting as Updater and Signer, it attaches that input's `PSTT_IN_UTXO` and signs it with `SIGHASH_ALL`, which commits to the complete transaction and clears the Inputs Modifiable flag.
5. The fee provider (or the user) finalizes each input and extracts the transaction.

The user's `SIGHASH_ALL | SIGHASH_ANYONECANPAY` signatures fix every output, so a third party that intercepts the PSTT cannot redirect funds. The only actions available to others are adding an input, which contributes additional fee, and removing one of the user's inputs, which leaves the remaining signatures valid but makes the transaction fail the per-color balance check unless the transaction was burning at least as many tokens as the removed input carried. In no case can funds be diverted to a different destination.

## Interactive variant (with change output)

If the fee provider uses arbitrary TPC UTXOs, it needs a change output, which must be part of the transaction before the user signs with a sighash type that commits to outputs.

1. The user, acting as Creator and Constructor, creates a PSTT with their token inputs and token outputs, leaves both the Inputs Modifiable and Outputs Modifiable flags set, and sends it to the fee provider unsigned.
2. The fee provider, acting as Constructor, adds a TPC input and a TPC change output, attaches `PSTT_IN_UTXO` for its input, clears both modifiable flags to declare construction finished, and returns the PSTT.
3. The user verifies the constructed transaction — token balances per color, the TPC fee implied by the provider's input and change output — and signs their inputs with `SIGHASH_ALL`. The provider signs its own input with `SIGHASH_ALL` likewise; the two can sign in either order or in parallel, with a Combiner merging the results.
4. Either party finalizes and extracts.

In both variants, the security of the user and of the provider rests on the rule that amounts and color identifiers are only trusted from a `PSTT_IN_UTXO` whose `hashMalFix` matches the input's outpoint: neither party can misrepresent the value or the color of the coins involved.

# Backwards Compatibility

Tapyrus has no earlier standard for exchanging partially signed transactions, so this TIP introduces no incompatibility within Tapyrus. Workflows that currently pass a raw transaction through repeated `signrawtransactionwithwallet`-style calls can adopt this format incrementally: any party in such a workflow can act as Creator and Updater.

This format is deliberately not interchangeable with Bitcoin's PSBT:

* The magic bytes differ (`pstt 0xFF` vs `psbt 0xFF`), so implementations of either format reject the other instead of misinterpreting it.
* The transaction data uses Tapyrus semantics (`features` field, outpoints referencing `hashMalFix`).
* The witness-related and Taproot-related key types of BIP-174 and its successors are reserved and unused, as is the global unsigned transaction of BIP-174.

Where a key type has the same meaning in both formats — partial signatures, sighash type, redeem script, BIP 32 derivations, finalized scriptSig, hash preimages, xpubs, version, proprietary, and the BIP-370 construction fields — this TIP assigns it the same type value as BIP-174/BIP-370 (with `PSTT_GLOBAL_TX_FEATURES` taking the type value of `PSBT_GLOBAL_TX_VERSION`). Implementations ported from BIP-370-capable code can therefore reuse their record handling unchanged, apart from the magic, the transaction serialization, the removed witness logic, and the version number (a PSTT carries version 0 where the equivalent PSBT would carry version 2; see the note in [Version](#version)).

# Rationale

**Key-value map container.** The container format is taken from BIP-174 unchanged. It is extensible (new key types can be introduced without breaking existing software), allows unknown fields to be carried through by intermediate parties, and makes combining independently updated copies of the same PSTT straightforward.

**A distinct magic.** A Tapyrus transaction with `features = 1` is byte-identical to a Bitcoin version-1 legacy transaction of the same shape, so a Tapyrus PSTT that reused the `psbt` magic could be parsed — and misinterpreted — by Bitcoin tooling. Distinct magic bytes make the two formats mutually unparseable, which turns a subtle semantic error into an immediate rejection.

**A single version, using the BIP-370 data model.** Earlier drafts of this TIP mirrored Bitcoin by defining two versions: a version 0 carrying a fixed global unsigned transaction (the BIP-174 model) and a version 2 carrying per-input/per-output fields (the BIP-370 model). This was collapsed into a single version for the following reasons:

* The BIP-370 model is functionally a superset: the fixed-transaction workflow is reproduced by constructing the complete transaction at creation and immediately clearing the modifiable flags.
* Bitcoin maintains both versions only because a large installed base of PSBT-version-0 software predates BIP-370. Tapyrus has no installed base, so carrying both models would double the specification and implementation surface (per-version branching in every role, exclusion rules between the two field sets, cross-version conversion) with no user to benefit.
* The constructable model is not an optional extra in Tapyrus: fee provision — required whenever a user holds only Colored Coins, since fees are payable only in TPC — depends on adding inputs and outputs after creation.

As a consequence, PSTT version numbers do not track PSBT version numbers: PSTT version 0 corresponds to the PSBT version 2 data model, and no PSTT version corresponds to PSBT version 0. Field type values, however, are kept identical to BIP-174/BIP-370 so that ported code and developer knowledge carry over.

**Only the full previous transaction, no standalone `TxOut` field.** BIP-174 added `PSBT_IN_WITNESS_UTXO` because the segwit signature hash (BIP-143) commits to the amount being spent, which lets a signer trust an amount that is presented without the full previous transaction. Tapyrus has no such signature hash: the legacy algorithm commits to neither the amount nor the scriptPubKey of the spent output. An amount — or a Colored Coin identifier — presented on its own would be unverifiable, and a lying Updater could make a signer misjudge the fee or the token being spent. Requiring the complete previous transaction lets the signer verify everything it is told by recomputing the transaction's `hashMalFix` and comparing it with the outpoint.

**Identification by txid.** In Tapyrus the txid (`hashMalFix`) never commits to scriptSigs, so the identifier is inherently stable under signing and finalization. The identification rule sets sequence numbers to 0, following BIP-370, because `hashMalFix` does commit to sequence numbers, which may legitimately change during a workflow.

**BIP-174/BIP-370 type-value assignments are kept, with gaps.** Reserving rather than reusing the type values of fields absent from this format (the global unsigned transaction `0x00`; witness-related values `0x01`, `0x05`, `0x08`, `0x09` in inputs and `0x01` in outputs; Taproot values) keeps every shared type value semantically identical between PSBT and PSTT. This minimizes the changes needed to port an existing, well-tested implementation, and prevents a class of bugs where a record is interpreted differently by the two ecosystems. For the same reason, `PSTT_GLOBAL_TX_FEATURES` takes the type value `0x02` of `PSBT_GLOBAL_TX_VERSION`, since the Tapyrus `features` field occupies the position of Bitcoin's transaction version field.

**No dedicated Colored Coin fields.** The color identifier is fully determined by the scriptPubKey of the previous output, which the signer already receives and verifies via `PSTT_IN_UTXO`. A separate field would duplicate that data and create the possibility of inconsistency. Applications that want to attach token metadata (e.g. names or icons per TIP-0020) can use the proprietary key type.
